# 2026-10-20 已确认状态识别修复

## 问题与影响

申购委托上午被识别为 `REPORTED`，下午券商返回状态码 `86` 后，现役适配器因没有对应映射而返回 `pending`，把每日完成状态降为未完成并触发收盘告警。安装的 xtquant 250807.1.2 未提供该数值的 `ORDER_*` 常量。

QMT Python API 文档的 `enum_EEntrustStatus` 定义 `ENTRUST_STATUS_DETERMINED = 86` 为“已确认”。[原文 PDF](https://www.qmtptrade.com/wp-content/uploads/2022/05/迅投QMT极速策略交易系统_模型资料_Python_API_说明文档_Python3.pdf)。确认代表委托状态，不代表成交或中签。

## 修复

- 适配器将明确的 `86` 映射为 `confirmed`，同时保留原始状态码；不依赖当前 SDK 是否提供对应常量。
- 对账将其记录为独立的 `CONFIRMED`，每日完成判断、午间等待判断、维护诊断和控制台均识别该状态。
- 外部已有且已确认的同证券委托继续阻止重复提交，不新建本程序的申购意图。
- 未知状态仍为 `PENDING`、继续告警并在摘要中显示原始状态码；不沿用先前“已报”来覆盖后续未知、撤单或拒绝回报。
- 申购范围、价格、数量、提交窗口、去重与通知发送入口不变。已有数据库无需结构迁移，不手工覆盖当日状态。

## 验证范围

新增隔离回归覆盖 SDK 无状态常量的 `86`、`255` 未知值、已报→已确认→收盘重复核对、北交所正常跳过、已确认外部委托防重、未知状态继续告警。端到端用例同时验证账本维护摘要、界面文案和通知摘要；网络被禁止，账户及委托均为合成数据。

本修复沿用 3.4.0 维护版本，以 Git commit、交付清单及 ZIP SHA256 区分代码身份。当前实际检查结果见仓库 `TEST_RESULTS.md` 最新日期部分；生产是否部署和自然运行验收必须另据目标机回执确认。
